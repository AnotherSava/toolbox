## Deliberately not stored — settled, don't re-propose

The table is **not** a lossless copy of the CSV, by decision rather than oversight. Four columns have no
Notion home:

| Column | Data present | Why it isn't stored |
|---|---|---|
| `Seat number` | none at all | nothing to store |
| `Seat type` | 15 of 195 flights (2014–2019, none since) | judged not worth a column; see below |
| `Dep_id`, `Arr_id`, `Airline_id`, `Aircraft_id` | every row | FR24-internal keys, meaningless outside FR24 and regenerated by every export |

Adding a `seat` column and backfilling it was considered on 2026-08-07 and **declined: the data is not
worth preserving.** `flights.py` used to parse and enum-decode `seat_type` into the `Flight` dataclass
only for `_row_properties` to drop it again; that dead parsing was removed with the decision, so these
columns are now read past entirely. `fr24-csv-quirks.md` still documents the seat-type enum, because
that describes FR24's export format rather than anything this code does.

One consequence worth keeping in mind, which is not a defect to fix: backfilling a new column would
rewrite existing rows, which is precisely what the append-only guarantee in `reconcile.py` exists to
forbid. Any such migration would have to be a deliberate, separately-snapshotted operation — another
reason not to drift into one casually.

Access is the **internal v3 API** (`token_v2` cookie) through `notion_tools.client`, not the official
REST API — the view configuration below is not expressible through the official API or the MCP server.
See `tools/notion/docs/learnings/notion-api-quirks.md` for the v3 surface in general.

## The display rules

These are implemented in `scripts/flights.py` and `scripts/notion_db.py`. They are **derived from the
whole flight history**, not from a row in isolation, which is why a sync re-parses the entire CSV and
only then filters down to the rows Notion is missing.

### Trips

A trip opens on departure from a home city and closes on arrival at one.
`HOME_CITIES = {"Moscow", "Vancouver"}` — matched on the **city** resolved via OurAirports, never on a
hard-coded IATA list. Moscow alone has five airports (DME, SVO, VKO, ZIA, CKL); an early IATA whitelist
missed ZIA and silently merged a Budapest trip into the Moscow → Vancouver migration two months later.
City matching also picks up any airport added in future.

Trips are numbered `T1..Tn` in chronological order and stored in a hidden `trip` select property.

### Row banding

The visible banding comes from a **separate** `parity` select property (`A` = `default`, `B` = `blue`),
set to `B` on even-numbered trips. One `conditional_color_rules` entry on each view, with
`background: {type: "match_property_value"}` against `parity`, makes every row inherit its option's
color — so each trip's block of rows alternates tint.

Two things to know before touching this:

- **Per-row `format.block_color` does not render in table view.** It persists via the API and is simply
  ignored by Notion's table renderer. Row coloring must go through the *view's* conditional rules.
- **Parity is a separate property from trip on purpose.** A single rule keyed to a two-option property
  bands arbitrarily many trips; keying the rule to `trip` itself would need one option color per trip.

### Bold text

Set on the combined `from_loc` / `to_loc` columns (`"City, Country"`), as an inline annotation on the
property value (`[[value, [["b"]]]]`):

- **Destination bold** — the stop is a real stay: `destination_is_stay` and the city is not a home city.
  A stop is *not* a stay when the next flight departs the same city within **12 hours** of arrival, which
  makes it a layover. Arrival times that cross midnight get a day added before the gap is measured.
- **Origin bold** — the origin city differs from the previous flight's arrival city, meaning the user
  travelled overland in between (e.g. Tivat → Dubrovnik by bus).

Home cities never bold on either side.

### Columns and views

25 properties; `date_sort` (real date, drives sorting), `parity` and `trip` stay hidden in every view.
`Full` hides the combined `from_loc`/`to_loc`; `Compact` hides the split code/name/city/country columns
plus aircraft, registration, class, reason and note. Both group by `trip` and sort `date_sort`
descending, then `dep` descending.

`date_sort` is the sortable date; the visible `date` is pre-formatted text (`"Jul 4, 2025"`). That
split predates the discovery that a custom moment-style `date_format` such as `MMM d` does render
natively — it works, it's just no longer the only way to get abbreviated months.

## v3 rules the sync depends on

- **Preserve select-option `id`s.** Row values bind to an option by its string `value`, but rewriting
  the options array without carrying each existing `id` over orphans every cell that used it. Never
  rebuild the `trip` options wholesale — read them, append the missing ones, write back.
- **A grouped view needs `query2.group_by` *and* `format.collection_groups`.** The groups array needs one
  entry per distinct value plus a trailing catch-all `{property, value: {type}}` for the unset bucket. A
  new `T69` with no group entry drops its rows into the catch-all instead of its own group. Group display
  order follows the option order in the schema.
- **Extend the groups array, don't regenerate it.** Regenerating resets `hidden` on every group, undoing
  any group the user collapsed in the UI. Append the missing entries ahead of the catch-all.
- **Views are user-tweakable.** The views were renamed in Notion's UI (`Compact table` / `Full table`,
  not the `Compact` / `Full` the create path emits) and carry hand-adjusted widths. That is exactly why
  the sync appends in place instead of re-running the import, which would build a second table and throw
  those tweaks away.
